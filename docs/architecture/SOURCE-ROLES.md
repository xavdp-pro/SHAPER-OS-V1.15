# Source roles, ownership and task navigation

The human–AI tandem steers the work. Source usability serves an acting agent's
precise retrieval before explanatory depth for a human audience.

## Task → owning sources → dependencies → action

| Task | Exact local entrance | Required neighboring owners |
| --- | --- | --- |
| Understand or change composition | [Composition](COMPOSITION.md) | Ecosystem, glossary, Rules 1/11/37, topology and fleet |
| Construct or specialize a service | [Boot](../agent/BOOT-CONTRACT.md) | Adopted LAW/rules, service's own intent, selected profile, dependency closure |
| Persist or recover state | [Rules 4/26](../../RULES.md) | Owning unit, Rules 12/16/30, schema/artifact and recovery contract |
| Run a persistent acting agent | [Common bridge](../intents/cognition-bridge.md) | Operating contract, Queue/Maestro, selected adapter and task authority |
| Govern or provision instances | [Governor](../contracts/governor.md) | Maker, typed recipes, fleet, bounded repair and selected host profile |
| Change shared terminology or ownership | [Vocabulary boundary](VOCABULARY-BOUNDARY.md) | Independent glossary, ecosystem source owner, affected referrers |

The complete route remains [CONTEXT-INDEX](../CONTEXT-INDEX.md) →
[GOVERNING-CORPUS](../GOVERNING-CORPUS.md) → full local foundation and applicable
specialist contracts. Targeted retrieval does not replace the constructor's
foundation obligation. Runtime briefs contain only the necessary scoped material.

## Custody contract

| Source role | Owns | Relationship |
| --- | --- | --- |
| [SHAPER ecosystem](https://github.com/xavdp-pro/shaper-ecosystem) | Common composition, cross-domain relationships and the five generic component mental contracts in `chapters/components/` and generic base contract `class:stem-cell` in `chapters/30-STEM-CELL.md` | This edition projects those meanings into its local operational laws; `navigation/OWNERS.json` identifies each exact component owner |
| [SHAPER glossary](https://github.com/xavdp-pro/shaper-glossary/blob/main/TERMS.md) | Stable concept IDs and vocabulary definitions | Local glossary explains usage and preserves compatibility aliases |
| SHAPER OS | Development/operational laws, adoption and reference contracts | Governs its declared scope; names source owners instead of absorbing them |
| Domain/service mental source | Domain intention, laws, interfaces and specialization | Refers to common invariants and supplies its own business meaning |
| Product realization | Code, interfaces, versioned configuration templates and tests | Realizes selected contracts; private SaaS and VOX code stay private |
| Project `-lab` | Working derivations, read coverage, reviews and execution/release evidence | Distinct private repository; references product revisions without becoming law; original conversations retain separate private custody |

Every project has a product source repository and a distinct `-lab` companion.
A product may itself be a mental source or an implementation. Source roles do
not impose a third repository on every project. Generic intentions/laws are
prepared for public reuse; private user realizations, configuration, data,
commercial code and work records stay within their owners' access boundaries.
Existing published history keeps its provenance; new raw dialogue and working
evidence belong in the private lab. A public intent link conveys no code rights.

## Hypertext contract

Identify each concept by the owning glossary anchor and each source by repository,
path and adopted revision. The ecosystem's
[structural relation vocabulary](https://github.com/xavdp-pro/shaper-ecosystem/blob/main/navigation/STRUCTURAL-RELATIONS.md)
owns canonical edge meanings and direction. Use `implements` for realization →
owned mental contract, `realizes` for actor → approved operation, and `runs-at`
for instance/runtime → placement. Every edge records its reason and owner.

Preserve local identifiers through explicit projections: `hosted-on`/`runs-on`
map to `runs-at`; local `requires` maps to phase-scoped `depends-on`; owner →
state `owns-state` inverts to state → owner `owned-by`; class → instance
`instantiates` inverts to instance → class `instance-of`. Resolve `contains`
by meaning: logical membership inverts to `member-of`, functional composition
maps to `composes`, and physical enclosure remains the selected hosting profile
with its instance → placement relationship. It is never one universal synonym.
Source relations such as `defines` and `refers-to` retain their explanatory roles.

For task closure, traverse only the selected phase's `depends-on` edges with
explicit mandatory/optional requirements, including optional branches selected
by that task. Other source links remain navigable without silently becoming
requirements. This integration-source closure is separate from the selected
realization's complete runtime/build/recovery dependency inventory.
The owning page is canonical; a projection labels its source and local scope.
Maintain reverse references for affected consumers so a changed contract leads
to its callers, specializations and dependent recipes. Containment is not
permission, hosting is not ownership, and a dependency is not authority.
Cross-repository referrer indexes identify references; they do not claim remote
files have already been updated. [Topology](TOPOLOGY.md) owns runtime dependency semantics.

Renames carry an old-to-new migration map: source role, class/version versus
instance ID, owner, visibility, redirects, submodule URLs, imports, image refs
and dependent documentation. Preserve compatibility identifiers until their
owners authorize a versioned migration. Publication and licensing follow their
own authorized sequence after source alignment.
