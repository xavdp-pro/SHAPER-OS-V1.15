## Public decision boundary

This record is the complete public statement of the direction. It does not rely
on unpublished dialogue identifiers or private source locations. The direction
was explicit; unresolved architectural interpretations remain marked open. The
preserved September profile's exact generic-law mapping is still to reconcile
and is not a newly ratified universal technology requirement.

## Adopted boundaries for this candidate

1. SHAPER OS stays agnostic, generic, clean and without code.
2. The repository carries intentions, rules, laws and the explanations needed
   to understand their interdependencies.
3. Concrete code is produced after interpreting SHAPER OS for an operational
   situation, outside this repository.
4. Better agents should be able to produce better code over time; the current
   implementation must not constrain the enduring framework.
5. The principal agent working with the human must know SHAPER OS thoroughly.
6. Preserve five human reading levels and two agent routes, medium and strong.
7. Preserve examples, original dialogue lineage and global coherence with the
   site, wikis, PodMesh and the related architecture.
8. Keep all SHAPER OS repository content in English, including human/agent guides.

## Vocabulary clarification

The operator originally conceived the concrete components as **bricks**. The
latest exchange does not authorize replacing that word with **packages** or
merging the two meanings. Check existing definitions and explain their relation
before changing the vocabulary.

## Reconciliation still required

successor ownership explicit. Existing operational choices, especially private
MariaDB per functional unit, require a scoped realization contract. Their
placement must preserve the target while keeping the generic core agnostic.
